# 诺文 UI 纪律（地图编辑器返工后立的规矩）

验收标准只有两条：**用户一眼看懂怎么用**、**符合诺文产品气质**（浅色、细线、薄荷绿点缀、文档式安静）。tsc 和构建通过不算验收。

## 1. 没亲眼看过，不许说"做完了"

- 改了用户可见的界面，交付前必须起 `pnpm run dev:web`，把用户路径真的点一遍：入口 → 每个模式 → 主要操作 → 刷新后数据还在。每一步都截图核对。
- 汇报时分两类写：已经亲手验证过的，和只过了类型检查的。没验证的不许写成"已完成"。
- 反例：地图编辑器只跑了 tsc 就交付。结果视野卡在左上角 320×200，「区域」标签既是当前图层又被隐藏。打开浏览器点一下就能发现。

## 2. 先写规格，再写代码

- 有设计稿时，以设计稿为布局规格，不只是配色参考。先逐屏列出：每个模式下用户看到什么、不该看到什么、每个控件叫什么。用户确认后再动手。
- 从用户任务往里设计，不要从引擎能力往外挂按钮。原型或引擎支持某个能力，不代表要给它一个按钮。

## 3. 控件按场景出现

- 只显示和当前模式有关的控件。例如草稿模式不出现标注图层。
- 一个控件只做一件事。切换当前图层和显示/隐藏要分开。
- 选项必须有可见的文字名称。只有颜色、名字藏在悬停提示里的色块不行。
- 不要靠底部一行小字教操作（如 "Alt+拖节点"）。必须写提示的操作，要么改成看得见的控件，要么只在它出现的那个场景里提示。

## 4. 复用产品现有的东西

- 分段控件、标签、按钮、滑条、空态，先去 `card-page.tsx`、`widgets.tsx`（时间线）、`style.ts` 里找现成的类名和 `--nv-*` token。只有确实没有才新写，并在汇报里说明原因。
- 不要出现浏览器原生样式（蓝色滑条、默认颜色选择框）。
- 同一块区域的底色必须一致，避免画布底色和外框底色不同、看起来像破纸。

## 5. 画布与生命周期的自查

- 依赖布局尺寸的初始化（取景、画布尺寸）必须在元素挂载、有真实尺寸后执行。容器尺寸变化时要重新计算。不能在早期 return 的分支里提前把它标记为"已完成"。
- 依赖会频繁重建的回调（如 `draw`）的 effect，要确认它不会把用户的缩放/平移重置掉。
- 在同一个事件里设置 A 状态、又读取 A 状态的旧值做判断，是必错的写法。

## 6. 汇报

- 结论先行，承认没做到的部分。不要用功能清单掩盖"界面还没亲眼看过"。
- 用户说"不对"时，先把截图里每个问题追到具体原因（代码位置 + 机制），再提修改方案。不要直接开改。
