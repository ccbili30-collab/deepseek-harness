# Agent Note: 进程外恢复检查点

Status: implemented

[English](2026-08-19-out-of-process-recovery.md) | 中文

## 问题

DeepSeek Harness 有两个会被修改的控制平面：检出或安装的源码树，以及 `DSH_HOME` 下的 profile 清单和 patch 文件。格式错误的 patch、不兼容插件或意外源码编辑，都可能让普通 Host 及其 Web 插件无法启动。如果恢复功能只是另一个 Host 或 Client 插件，它就会与自己原本要修复的对象共享同一个故障边界。

用户数据树还包含凭据、Session、附件和工作区内容。如果把整个 `DSH_HOME` 当作一个可恢复镜像，配置回档就可能在无提示的情况下回退对话或替换密钥。反过来，如果快照存放在 `DSH_HOME` 内，它也可能随受损安装一起消失或变得不可读。

## 决策

在发布的 `dsh` launcher 中加入恢复模式。参数解析在导入应用启动、profile 组合、Cordis 或任何插件包之前分派该模式。其实现只使用 Node 内置模块，因此普通 DSH 启动图失效时仍然可以调用。

恢复检查点存放在独立的恢复根目录中，位于源码树和 `DSH_HOME` 两者之外。每个不可变检查点包含带版本的 manifest、SHA-256 哈希、源码身份信息和文件副本。默认范围包括：

- Git 跟踪的源码文件，以及未被忽略的未跟踪源码文件；
- `DSH_HOME` 顶层的 `cordis.patch.yml` 和 `settings.yaml`；
- 每个 profile 的 `package.json`、`cordis.patch.yml`、`pnpm-lock.yaml` 和 `pnpm-workspace.yaml`。

凭据、含密钥的环境文件、Session、附件、storage、生成的依赖目录和普通工作区内容由策略明确排除，而不只是依赖某个默认 glob。以后可以增加显式且单独命名的数据备份范围，但恢复检查点绝不能让人误以为它保护了这些数据类别。

创建检查点时，系统先写入临时目录；只有当每个复制文件都与 manifest 哈希一致时，才通过一次 rename 发布。恢复时，系统先校验所选检查点，确认请求的源码和 `DSH_HOME` 与记录的身份相符，并为当前状态自动创建一份救援检查点。恢复写入只允许落在 manifest 声明的控制平面路径中，使用同目录临时文件和原子 rename，并要求显式确认 token。第一版只允许把源码检查点恢复到捕获时的同一个 Git commit；版本迁移属于另一项操作。

Web 恢复中心只是这条恢复边界的轻量客户端。侧边栏底部的电源菜单——展开时在“设置”右侧，收窄时在其上方——只包含创建、回档至最近检查点和安全关机。设置页的“恢复与回档”栏目负责检查点历史、路径详情、校验、任意选择和精确 ID 确认；快捷回档会显示最近检查点 ID，并要求再次明确确认。两个界面都不拥有快照存储和文件写入权。即使 Web 部署信任某个局域网地址，恢复命名空间中的所有 Remote 也会被限制为仅允许本机回环访问。

Host 会在请求有边界关停前启动一个脱离当前进程的 guardian。guardian 等待 Host 进程退出，运行已经载入内存的恢复实现，创建救援检查点，恢复所选状态，然后按原 launcher 命令重启。普通 Web 树无法启动时，命令行恢复模式仍是手动入口。

## 备选方案

**把恢复实现成普通 DSH 插件。** 这种方案容易分享，也能提供所需 UI，但无法修复在插件 apply 之前就失败的 Host。因此它只适合作为前端。

**依赖现有 startup-guard 插件。** 现有社区项目已经展示了启动标记、profile 备份、救援页面或外部 guardian。它们的恢复范围和启动保证各不相同，其中一些还会在启动诊断时运行插件代码或修复 Session 文件。核心恢复路径只吸收其中有用的设计思路，不引入第三方运行时依赖，也不自动修改 Session。

**只使用 Git。** Git 适合管理源码历史，但并不拥有 `DSH_HOME` 下的 profile 清单，无法单独表示用户安装的插件状态，而且从恢复 UI 中直接调用时很容易产生破坏性操作。恢复系统记录 Git 身份，但采用独立且不可变的检查点格式。

**复制整个 `DSH_HOME`。** 这会生成一个表面完整的镜像，却把配置回档与对话、凭据和工作区回档绑定在一起。这些数据需要各自独立的保留和授权策略。

**维护两套完整 DSH 安装。** 把开发用途和日常用途隔离开来很有价值，可以缩小故障影响范围，但重复安装本身不提供命名历史、完整性校验，也不能安全恢复当前正在使用的副本。恢复存储是隔离安装的补充，而不是替代。

## 测试

- `dsh recovery` 的解析和执行不会导入 DSH boot、profile、Cordis 或插件模块。
- create、list 和 verify 操作可以在无密钥的真实进程测试中，针对显式指定的源码、`DSH_HOME` 和恢复根目录运行。
- 只有当 manifest 和所有 payload 哈希都校验通过后，检查点才可见；中断创建不会留下可选择的检查点。
- 默认检查点包含文档所列的源码和 profile 控制平面文件，并以机械方式排除凭据、含密钥的环境文件、Session、附件、storage、依赖树和工作区。
- 恢复在修改目标前拒绝不匹配的源码 commit、不匹配的根目录、损坏 payload、缺失确认以及路径穿越。
- 恢复在首次写入目标前创建并校验救援检查点；聚焦破坏性测试证明错误源码编辑和 profile 插件编辑均可恢复。
- 恢复绝不写入所选源码树和 `DSH_HOME` 之外；报告给出已恢复文件数和后续依赖安装状态，文档明确列出按策略排除的数据。
- 侧边栏底部的 Web 入口在没有检查点时仍然可见，只保留三个电源操作，并把恢复委托给负责停止和重启 Host 的独立 guardian；精确 ID 管理留在设置页。
- 即使部署声明了受信任的局域网地址，恢复 Remote 仍仅限本机回环访问。
- 中英文 CLI／恢复文档对范围、排除项、guardian 路径和手动回退方式作出一致说明。

## 后果

直接通过 CLI 恢复无法让并发运行的 Host 自动静止，因此它要求 `--offline`，并使用记录的前置状态保护每项修改。Web 路径则会在请求 Host 关停前把任务交给 guardian；guardian 只有在原 PID 退出后才开始恢复。

恢复 profile manifest 后，原有 `node_modules` 树可能不兼容。恢复报告会明确标示依赖需要重新协调；本版 guardian 刻意不会自动运行包管理器。

如果 launcher 只存放在可变源码检出目录内，它也可能随源码一起损坏。第一阶段先建立不依赖导入的边界；在功能可以声称能够应对已安装 CLI 本身被删除之前，还需要把一个小型的已知良好 launcher 封装到外部恢复根目录中。
